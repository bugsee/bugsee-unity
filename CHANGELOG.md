# Changelog

All notable changes to this package are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [0.1.0] - Unreleased

### Fixed

- `AddAttachmentFile` on a managed report (`CreateReport`) copies the file under the app's internal cache directory (Android) or `Application.temporaryCachePath` (iOS), falling back to the system temp path, instead of `Path.GetTempPath()`, which is `/data/local/tmp` and not writable by the app on some Android 11 devices; the call returned null with no log. A failed copy now logs a `[Bugsee]` warning. Copies left behind by a crash are removed at startup after a day. Fixes #188, #177.
- Managed exceptions the SDK reports from Unity's log text (`FromUnityLog`) no longer forward a hex found in that text as a frame address. That path runs when Unity's text is the only copy of the exception: another log handler replaced Bugsee's later without chaining, `Report` failed or was skipped so the echo was not expected, or something logged `LogType.Exception` with no exception object (a normal `Debug.LogException` or uncaught exception reaches the throw path and is unaffected). The text has no native IPs and cannot say which image a number belongs to, but the old code still forwarded any `0x` value of 8 or more hex digits and any `#NN pc ...` line (an absolute address, or a pc of another library such as `libunity.so`) while the worker resolves `frames[].address` against `moduleUUID` as a module-relative RVA, which files a plausible but wrong C# line. Those frames are now symbolic only. Fixes #105.
- **iOS:** the Run Script no longer passes empty `--version` / `--build` to `bugsee-cli debug-files upload` when the export has no `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION` (a Unity export sets neither): the values come from `BUGSEE_VERSION` / `BUGSEE_BUILD`, then the built app's Info.plist (`CFBundleShortVersionString` / `CFBundleVersion`, the Player Settings' version and build number, which is what the SDK reports), then those build settings (a difference from the plist is noted), and a flag with no value is left out. Fixes #162.
- Values that cross to native or become identifiers no longer follow the device's culture (a decimal-comma device wrote 1,5; a bool was "True"): the iOS wrapper context, the bool options of the exception pipeline, the integer option parsing and the Editor build identity use invariant text. Side effect: the fallback build number (used when neither the iOS build number nor the Android version code is set) and the `legacy-templates` backup folder name are now always Gregorian digits, so the fallback number of a th-TH device (Buddhist year 2569) is numerically lower on the first build after upgrading, and on ar-SA and fa-IR (Hijri and Persian years) it is higher (symbol-upload metadata only). A source scan and per-culture tests guard the paths.
- Docs and sample: the managed payload's `cause` chain is not read by the worker yet (#104); the docs say so, and the sample has a `nested` scenario (a handled exception with a three-level `InnerException` chain; self-checking: `[Sample] nested PASS|FAIL`).
- **Android:** a managed exception's client signature no longer depends on the Java call site of the wrapper. The Android SDK hashes the Java stack of the throwable it is given into the report signature, and `UnityManagedException` was built where the wrapper called the SDK (the JNI entry, the main thread's or a worker's frames), so the SDK's signature differed by calling thread. `UnityManagedException` now carries no Java stack: the SDK's signature is the exception class, the domain, `handled` for `LogException` and the payload `signature`. The payload `signature` still hashes the raw managed stack, which on Mono runs on to the calling thread's root, so it still varies per thread until #217. Also removed the `$$signature` and `moduleUUID` options the bridge put in the exception options map: the SDK reads only `signature` from the reason JSON, the worker only `moduleUUID` (and `il2cppLinemapId`), and the options only ended up in the report's logging options. The `skipFrames` exception option has no effect on Android any more (it only trimmed the Java stack of the wrapper's throwable in the SDK's hash). Verified on an HONOR WOD-LX1 (Android 14) with the new `sigthreads` scenario (the SDK's own signature function for the same payload handed over from the main thread and from a worker: equal; a plain `java.lang.Exception` control differs). What the SDK still adds (`handled`) and what the worker does with the signature are not wrapper-side, see `Documentation~/exception-signatures.md`.
- **Android:** the Editor no longer logs "attaching launcher icon ... to the mapping upload" when no mapping is uploaded (Minify off); the line is now logged only just before a mapping upload that carries the icon (#168).
- **Android:** the split-APK build id read compared file times with a build start shifted by the machine's UTC offset; it now reads `buildStartedAt` as UTC (#169).
- **iOS:** lifecycle events that arrive before the managed callback is registered (for example from a launch the host made natively before any C# call) are held, up to 128, and replayed in order on the main queue after the registering `Launch` or `Relaunch` call, as on Android, instead of being dropped. `Relaunch` now registers the wrapper like `Launch`.
- **iOS:** a lifecycle payload that is a dictionary reaches `LifecycleEvent` / `ILifecycleEventListener` as a `Dictionary<string, object>`, as on Android, not as raw JSON text; a one-key dictionary is no longer mistaken for a string.

### Changed

- `ResetVideoCapturePermission()` on iOS no longer does nothing silently: it logs a warning once per process (iOS has no capture permission to reset). Its doc comment states the per-platform behavior. `IReport` and the docs now say that both SDKs have per-report screenshot members that the wrapper does not expose yet (bugsee-unity#224); `CaptureScreenshot = false` omits the screenshot, secure rectangles and blackout only redact it, attachments cannot do either. New sample scenario `videoperm` counts the warning (`[VIDPERM] RESULT`).
- iOS launch options (#97): typed `IOSLaunchOptions` properties and `Options` constants for the iOS 7.0.0-beta7 keys that were reachable only through `SetCustomOption`: `CrashSignals` (new `[Flags] CrashSignals`), `CaptureOnDeviceSymbolication`, `CrashSwiftAsyncStackTraces`, `CrashFillEmptyExceptionStacks`, `CaptureWebSocket`, `CaptureAVPlayer`, `CaptureSampleBufferDisplayLayer`, `CaptureCameraPreview`, `CaptureBluetoothStatus`, `CaptureDiskSpace`, `CaptureDeviceNetworkNames`, `CaptureVideoPrivacyBlur`, `CaptureVideoMinFrameRate`, `CaptureVideoMaxFrameRate`, `DataEncryption` (new `DataEncryptionMode`), `BuildTarget`, `BuildType` and `ReportingUIStyle` (new `ReportingUIStyle`), plus `OptionsBuilder.SetCrashHandlerType/SetCrashSignals/SetDataEncryption/SetReportingUIStyle`. All are iOS only: `OptionPlatformGate` drops them from an Android launch, and each property documents its default and platform. `capture.logs.oslog` (permanently disabled), `capture.status-bar-info` (read only by a DEBUG SDK build) and `capture.mach-exceptions` (removed from the SDK, which ignores it with a warning; use `CrashHandlerType`) stay unexposed. The frame-rate limits are clamped to 0..30 by the SDK. The sample presets use the typed properties and the `options` scenario checks on both platforms that iOS reports every iOS-only key and Android none.
- New `DeleteScope` and `Bugsee.DeleteCollectedDataOnDeviceAsync(DeleteScope scope = DeleteScope.Everything)` (a `Task<bool>`: true when the SDK reported the data deleted, false when it refused or gave no answer in time) and `Bugsee.DeleteCollectedDataOnDevice(DeleteScope scope)` (#101). `CaptureOnly` and `CaptureAndIntermediate` keep the report bundles waiting for upload (Android `deleteCollectedDataOnDevice(includingIntermediate, false, ...)`, iOS `deleteCollectedDataOnDevice:completion:`); `Everything` is the default and what the unchanged `DeleteCollectedDataOnDevice()` still does. Deletes run in request order and a narrow one is never widened: on iOS, when no launch is deferred behind it, one of the same scope as the wipe in flight shares it and its result, and one of another scope waits for it; on Android a queued delete shares the one before it only when it has the same scope. The "kept" data is the native SDK's on disk; every scope stops the SDK, which drops an unfinished managed report and upload as `Stop` does. A timeout completes the task with false (not a `TimeoutException`), and a value that is not a `DeleteScope` throws `ArgumentOutOfRangeException`. New sample scenario `deletescope`.

- **Android:** a map, list or array passed to the SDK (report attributes set in a report handler, `Trace` values, event parameters, `LogException` options, span attributes, breadcrumb-filter maps) is sent as valid JSON text (at most 8192 characters, whole trailing entries dropped, cycles written as null) instead of its type name; an enum goes as its integer value, a `byte[]` as base64, a float as the double that prints the same, and other types as culture-invariant text (#154; references #143 and #147, which stay open for the iOS `ToString()` and the remaining `Trace` parity).
- **Android:** `IReport.GetAttribute`, `IReport.Attributes` and `Bugsee.GetAttribute` now return `long` for every integer and `double` for floating point (as iOS), where they returned the boxed width that was set (`int`, `short`, `byte`, `float`). Code that unboxes with `(int)` must use `Convert.ToInt32` or `(long)`.
- Docs: `CaptureBreadcrumbs` is off by default on both native SDKs, so `Bugsee.AddBreadcrumb` records nothing and the breadcrumb filter is never called until it is set; `Bugsee.Log` lines skip the log filter on both platforms. Added to the XML comments and the documentation.
- The wrapper build id of a release is now a real one instead of `dev`. `Tools~/scripts/stamp-wrapper-build.sh` writes the short hash of HEAD (or an id you pass) into `BugseePackageVersion.Build` and `UnityWrapperIdentity.BUILD`; commit that, then tag. `Tools~/scripts/check-release-build.sh vX.Y.Z` (run it before `git push --tags`; the `Release check` workflow repeats it on a pushed `v<digit>*` tag, but can only report) fails if the constants are `dev`, disagree, name a commit that is not an ancestor of the tagged commit, if anything but CHANGELOG and the build/version lines of the two constant files, `package.json` and `versions.env` changed since it (a changed SDK pin fails), or if the tag is not `v<package.json version>`. The release branch must not be merged back into `main` (a CI job requires `dev` there); the steps are in `DESIGN.md`, "Releasing". `main` keeps `dev`, which the wrapper still reports as no build (so `environment.sdk.wrapper.build` is set only on a stamped release), and `update-native-sdks.sh` no longer overwrites the build with the current HEAD (it keeps the file's value).
- New launch option `CaptureUnobservedTaskExceptions` (Unity-only, default true, needs `CaptureManagedExceptions`): set it to false to stop reporting `TaskScheduler.UnobservedTaskException` as a handled error. The default stays on, as in the Bugsee .NET (MAUI) SDK, whose `HandleTaskExceptions` defaults to true and files the same event as a handled exception. Changing it on `Relaunch` takes effect (the subscription is re-synced; `TreatUnityLogExceptionsAsFatal` is still read at the first launch only). Unity raises the event only after the faulted Task is garbage-collected (seen: 14 to 50 s after a forced GC), so the report can be late, and fire-and-forget tasks that fault on purpose are noise for some apps.
- New sample scenarios `attach` and `unobserved` (`BUGSEE_E2E_SCENARIO` / intent extra `bugsee_e2e`; `bugsee_unobserved=0` / `BUGSEE_E2E_UNOBSERVED=0` switches the option off): they log, tagged `[ATTACH]` and `[UNOBS]`, what the SDK accepted for empty and MIME-less attachments and whether an unobserved task exception fired after a forced GC.

- Android Mono managed frames get a C# file and line only in a Development build. Verified on an HONOR WOD-LX1 (Android 14, Unity 2021.3.45f1, ARMv7): a Development build ships `Assembly-CSharp.pdb` and `Bugsee.Runtime.pdb` (portable) in `assets/bin/Data/Managed` and prints `at Ns.C.M (System.String marker) [0x00001] in /path/File.cs:713`; a Release build ships no pdb or mdb and prints `[0x0000b] in <module-guid>:0` (an IL offset, no file or line). Nothing resolves that offset: the CLI's `PortablePdb` debug-file type is a scaffold and the worker has no Portable PDB support (tracked as a cross-repo plan, not done here). A Release Mono Android build now logs a one-time build-time warning that says so and names the Development Build (not for store builds) and IL2CPP line information where Unity offers it (never fails the build). The docs table that listed Mono as "file:line: yes" is corrected.

- iOS `Bugsee.IsBlackout` now reads `+[Bugsee isBlackout]` (new `_bugsee_is_blackout` export) instead of a flag the wrapper kept, as Android reads the SDK; no behaviour change with 7.0.0-beta7, where only `StartBlackout`/`EndBlackout` change the flag (the iOS SDK keeps it across Stop and a later Launch, unlike Android). Fixes #135.
- The wrapper's option surface is now checked against the option manifests the native SDKs publish (Android 7.4.2, iOS 7.0.0-beta7, `download.bugsee.com/sdk/options/...`, vendored by the new `Tools~/scripts/update-options-manifest.sh`, which `update-native-sdks.sh` runs after a bump). `OptionsManifestTests` fails when an `Options` constant is not a native key, a setter type or enum value disagrees, a native option is neither exposed nor listed as not exposed (the known gaps are frozen with their issues #96, #97, #108), or a hardcoded enum fallback differs from the SDK default. Found by it: Android `config.max-data-size` and `config.notify-flush-delay` also have no constant (added to #96's list).
- Removed dead bridge code: the iOS exports `_bugsee_add_secure_rect`, `_bugsee_remove_secure_rect`, `_bugsee_remove_all_secure_rects`, `_bugsee_get_device_id` and `_bugsee_cancel_managed_report_upload` (no-ops or never imported; secure rectangles go through `_bugsee_set_secure_buffer`, upload cancellation through `_bugsee_invalidate_managed_report_uploads`), their two unused C# DllImports, the unused `BugseeBridgeSetAttachmentFileNameIfNeeded` helper, and the `BUGSEE_IOS_LEGACY_EXCEPTION_API` (bugsee-cocoa up to beta6) branches. The delayed-delete retry block no longer trips `-Warc-retain-cycles`. A `BUGSEE_IOS_SDK_LOCAL_PACKAGE` that points at a bugsee-cocoa build older than 7.0.0-beta7 no longer compiles (the bridge uses `logException:reason:domain:skipFrames:`) instead of falling back to the old API. Also removed the unused `ToJsonLiteral` and `JsonString` helpers in `IOSBridge.cs`.
- In the Unity Editor and on unsupported platforms (standalone, WebGL) `Bugsee.SetAttribute` now applies the same `AttributePolicy` validation as the device bridges and throws `ArgumentException` for an invalid key or value; it still stores nothing, so `GetAttribute` returns null there.
- The iOS bridge now warns once at the first launch on the iOS or tvOS simulator (in the Unity log and the native log) that native crashes, hangs and managed exceptions (handled and unhandled) are not reported there, only from a device: the SDK's simulator build has no crash reporter. The docs say so, and what still works (bug reports, logs, events, video).

- Sample README (#119): no longer says the hills cover "the public facade" without qualification (they reach every `Bugsee` method except the synchronous `Relaunch(options)`, not every member of the objects it returns; the unreachable ones are listed), says Android launches with `VideoMode.V2` and that `DirectBuffers` needs the `bugsee_frame_pusher` intent extra, says the filters are observable only through the HUD counters and the filter check, and documents the HUD status lines, all 13 hills, every e2e scenario (including `options`, `netfilter`, `blackout`, `attrsnoop`/`attrsedit` and `severity`/`severitylabels`), the launch switches per platform and the `E2EBuild` environment variables. The `Tools~/scripts/e2e-android.sh` header points at the README scenario table.

- Documented the secure-rectangle origin: `AddSecureRectangle`/`RemoveSecureRectangle` take a top-left-origin pixel rectangle on both platforms and pass it to native unchanged (no flip from Unity's bottom-left screen space). Behaviour is unchanged; the docs now include a conversion helper.

- Documented what `Launch`, `Relaunch`, `Stop` and `DeleteCollectedDataOnDevice` guarantee on each platform, the 10 s soft and 60 s hard deadlines, and the residual races: iOS, a late native stop (or wipe) can still affect a `Launch` made after the 60 s give-up; Android, a late launch/relaunch result after the hard reset is ignored when no stop intent is set, a queued `Launch` can run while a native delete is still wiping after the reset, and a delete handed to native can finish after its 10 s warning.

- Android Mono builds cannot symbolicate native frames inside the Mono runtime (`libmonobdwgc-2.0.so`, `libmono-native.so`, `libMonoPosixHelper.so`): Unity 2021.3 has no Mono ARM64 and those libraries have no GNU build-id. Documented in the Player Settings checklist, and a Mono Android build now logs a one-time warning at build time regardless of symbol upload settings (the build is never failed).

### Fixed
- iOS: after `SetNetworkEventFilter`, every request no longer reaches the SDK with an empty error, an empty body and an empty url. Unity's `JsonUtility` writes a null string as `""`, so the whole event went back and native applied it (a non-nil two-key `error`, empty `NSData`, `@""`). The filter result now carries only the fields the filter assigned (setter called; `Headers` also when the map was edited in place), whatever value they hold, so an untouched event keeps its native values and `Body = ""`, `Body = null` or `Url = null` still apply (including a body native could not read as text). An event the filter returns instead of the one it was handed is applied onto the original, so it is written in full (null and empty fields clear: the original's body, headers and error do not survive) and without a timestamp (the original's time stays). Native treats an empty error name or description as removal, so clearing an error with empty strings leaves no error. Header values that are null are sent as empty strings and numbers are written culture-invariant. Channel submits (a fresh native event) omit null and empty strings. New e2e scenario `netfilter` in the sample.
- iOS: log event and breadcrumb filter results no longer go through `JsonUtility` either (#160), which wrote every untouched null string as `""` (an untouched breadcrumb got an empty category, message and type applied). The result now carries only the fields the filter assigned (`Message`/`Level` for a log event; `Category`, `Message`, `Type`, `Level` and a touched `Data` for a breadcrumb), whatever value they hold, and an event the filter returns instead of the one it was handed is written in full. The SDK does not tell a null string from an empty one on iOS: an empty log message drops the line, and an empty breadcrumb category, type or message ends up omitted. The sample `filters` scenario gains a pass-through phase, and `BridgeTests` apply result dictionaries to a real SDK log event and breadcrumb.

- Report attachments follow the report contract: empty bytes are a valid attachment (iOS `AddAttachmentBytes` returned null for `new byte[0]` and the bridge dropped an empty `dataBase64`; the Android managed report did the same) and a missing MIME type stays unset (iOS, for a null MIME type, and the Android managed report, for a null or empty one, filled in `application/octet-stream`; the iOS add-time path sent that default to the SDK, and an iOS attachment given non-UTF-8 data through `SetData` was relabelled `application/octet-stream` even over a MIME type you set). A live Android attachment's `SetData(new byte[0])` now empties it (it returned early and kept the old content; `openStream()` opens the file without append, which truncates it: read from the SDK source, not run on a device). Null data is still refused. A null `mimeType` on the Android live report goes to `addAttachment` as it is (the SDK leaves it unset; checked over JNI on an API 30 emulator). On iOS the extended-report path (`CreateReport` then `Upload`) builds a `BugseeAttachment`, which in 7.0.0-beta7 has no MIME type property, so a MIME type given there is not applied (unchanged); only the add-time path (`addAttachmentWithData:name:mimeType:`) carries it. The iOS bridge test hooks cover both report paths.
- Report handlers, and the Android log filter, no longer act after the native SDK has moved on (the network and breadcrumb filters are unchanged: see the documentation for their limits). The SDK carries on with a report unchanged after `ReportHandlerCallbackTimeout` (30 s by default on Android and iOS; iOS does not read the option). On Android the handler waited in the Unity main-thread queue, which is not drained while the app is in the background, and then ran against a report the SDK had already left; the before-phase handler is now skipped (a warning is logged), while the after-phase handler, usually a notification, still runs late with a completion that only acknowledges. The report and its attachments handed to an Android handler stop accepting edits once its completion has run, so a handler that kept them cannot change the report afterwards. On iOS a slow `completionCallback` wrote its edits into that report; a reply after the deadline is now acknowledged without applying them (the iOS handler runs on the main thread, so a skip there is not expected). The completion is honoured once, and a handler that never calls it is abandoned a second after the deadline, which releases the native completion (Android) or the native entry, report and snapshot files (iOS). On Android the log filter is dropped by the SDK after 10 s without a reply and its callback object is reused for the next event, so the wrapper no longer replies to a log filter after that window (a late reply could complete the next event with this one's data; the network and breadcrumb filters have no SDK timeout in 7.4.1/7.4.2 and are unchanged). The Android timeout option is now read at most once a minute and kept when unreadable. Filters get no pass-through default: an unfiltered event would leak what a redaction filter removes. Remaining Android SDK issue (the SDK does not match a late log-filter reply to its event) and the other limits are in "Filters and the report handler while the Unity loop is paused" in the documentation.
- Reports from Unity now carry a managed view hierarchy. Both platforms answered the SDK's `requestData("vh")` with `null`, so the report's `viewtree` had only the native tree (a single Unity surface). The wrapper now replies with the loaded scenes, and the DontDestroyOnLoad objects, as one JSON root node (`class_name`, `bounds` `[x, y, w, h]`, `id`, `options`, `subitems`; the shape in the specs' `sdk/wrapper-data-requests`): every active GameObject with the type of its first component (`class_name`), all its component type names (`options.components`) and its name (`options.name`). Bounds are Unity screen pixels with the origin at the top left on Android, and points on iOS (Unity's width over the screen's width in points, so a Plus, mini or Display Zoom device is right); uGUI is read from its canvas (Screen Space - Camera with no camera counts as overlay), anything else from its Renderer, a container from its children, and a box is clamped to one display of margin around the screen. The SDK asks when it takes a report snapshot on its main thread (iOS: the Unity thread, so the reply is made inside the request) or when `Bugsee.CaptureViewHierarchy()` runs; on Android a snapshot on the UI thread is answered after it, so that tree reaches the next report. The walk runs on Unity's main thread, stops at 1500 nodes, depth 24 or about 80 ms (the node where it stopped has `truncated: true`), the whole build is capped at 120 ms, and a request that waited more than 250 ms for the main thread is skipped. A request made while Unity's main thread is inside a synchronous SDK call (`LogException`, an unhandled exception) is answered null at once: the SDK files that report on the calling thread and would wait for a reply only that thread could give. A failing object loses its own subtree, not the tree. Privacy: no component is asked for a value, so UI text never reaches the tree; GameObject names are sent (runtime-built names can carry app data), except that a node whose box overlaps a `Bugsee.AddSecureRectangle` rectangle loses its name and component list. Limitations: on Android the bounds assume Unity's surface sits at the window origin and renders at display resolution (`Screen.SetResolution` or a status bar offset shifts them); the viewer reading a string `managed` is the specs' open item 2.
- `environment.sdk.wrapper.build` carried the literal `dev` in every build, since no build id is stamped into the committed constants. The wrapper now reports no build (null on Android and iOS, `build` omitted from the iOS `wrapper_info`) while the value is empty or `dev`, instead of a placeholder that looks like a build id. A real id stamped into the constants is reported as before; where it comes from at release time is set by the release flow in `DESIGN.md` ("Releasing"), see the entry under Changed.
- Sample action bugs (#115): Get/Clear Attr use the key last set in the Set Attr form (shared with the debug panel) instead of a hard-coded `field.note`; Clear ID clears only the user identifier, not every attribute; the deprecated Pause/Resume bubble alternates `Pause()`/`Resume()` per tap and shows the state (it used to call both back to back); the hazard orb's status shows the `LogException` result with a counter that also goes into the exception message; E/Space runs the selected action of a hill (Q/Tab cycles, `> ` marks it) instead of always the first; `RelaunchSdk` logs its exception. The keyboard shortcuts are ignored while a form is open or a text field has focus. The exception counter is a marker only (it does not change report grouping). New e2e scenario `actions` drives these paths on a device.
- Option gating: iOS no longer receives Android-only keys, which it keeps verbatim (they showed in `GetLaunchOptions` and in `sdk.options` of every report): `capture.video.secure-scrolling`, `fullscreen-remember-decision`, `fullscreen-keep-running`, `config.report-handler-callback-timeout`, `performance.upload-mode`, and the Android keys `Options` has no constant for (`detect.crash-ndk`, `crash-ndk.tombstone-logs`, `detect.anr.sampling`, `detect.hang.sampling`, `detect.memory_leaks[.mode|.deep_sample_rate]`, `detect.thread_leaks`, `detect.exit.bg_low_memory_as_error`, `config.max-pending-reports`, `config.max-pending-report-age`). ### Changed

Behaviour changes to be aware of. 0.1.0 is not released, so these correct earlier unreleased work.

- Native SDKs: Android `bugsee-android` / `bugsee-android-ndk` 7.4.2 and iOS `bugsee/spm` 7.0.0-beta7.
- Android `DeleteCollectedDataOnDevice` now stops the SDK whenever it is not stopped and also deletes finished
  report bundles, **including reports that were not uploaded yet**. Before, it kept all finished bundles
  (the native two-argument overload does not delete them) and could delete before the SDK had stopped.
- Android `TestCrash` now crashes the app with an uncaught exception thrown on the Android main looper, and
  returns before the process dies. Before, the exception came back to C# as a caught `AndroidJavaException`: no
  crash was reported and the app kept running.
- iOS `IsLaunched` is now true only while the SDK is in its `Launched` state (it is false during the short
  `Launching` window), and `Status` reports the SDK's own state, including `Launching` and `Stopping`.
  `Stop(completion)` runs the completion when the SDK reports the stop finished, and only one native stop runs at
  a time: a second `Stop` or a delete during it waits for it. A `Launch` or `Relaunch` requested while a stop is
  in flight is deferred until it finishes (the latest request wins; a later `Stop` or delete cancels it). A
  completion is dropped when a `Launch` or `Relaunch` happened before the stop finished, and when the stop could
  not be started because the main thread did not take the call within 5 s. After 10 s the call's own completion
  runs with a warning while the native stop stays in flight (launches stay deferred); after 60 s the wait is
  abandoned and deferred launches run.
- iOS `DeleteCollectedDataOnDevice` now runs in request order, as on Android, and is no longer skipped. Before, a
  delete did nothing (with a warning) when a `Launch` or `Relaunch` ran between its request and its teardown:
  `Stop(() => Launch(...)); DeleteCollectedDataOnDevice();` and, after the 60 s give-up on a stop, a delete
  queued behind it. Now the wipe runs first, and a `Launch` or `Relaunch` requested after it waits until the SDK
  reports the wipe finished (it clears its files on a background thread), with the same 60 s give-up as a stop.
  A delete that shares a stop with `Stop(() => Launch(...))` runs ahead of that completion. A delete that finds
  the SDK still stopping waits for that stop (up to 10 s) instead of stopping it again; if it never
  stops, or the SDK reports the wipe failed, a warning is logged and a waiting `Launch` still proceeds.
- Android `Launch`, `Relaunch` and `DeleteCollectedDataOnDevice` run one at a time, in request order, on the main
  thread, while `Stop` is not held in that order (it starts or joins a native stop at once, and drops queued
  `Launch`/`Relaunch` requests; only the hand-off from another thread is queued, as for every Android lifecycle call): a `Launch` or `Relaunch` during a stop is deferred, a
  `Relaunch` is ignored with a warning unless the SDK is `Launched`, a refused `Launch` no longer cancels a pending
  delete, and a late launch result after a newer `Stop` is stopped again. In-flight operations answer their callers
  after 10 s and are abandoned after 60 s.
- iOS wrapper-channel network events are sent with the SDK's own event types (`before`, `complete`, `cancel`,
  `error`) and a Unix-millisecond timestamp. Events with a stage iOS cannot represent (`Redirect`,
  `RequestTimingsReceived` and `WebSocket`) are **dropped with a warning**.
- `GetAttribute` keeps the kind of a scalar on both platforms: a string reads back as `string`, a bool as `bool`,
  an integer input as an integer and a floating-point input as floating point (a whole-valued one such as `1.0`
  stays floating point on iOS, it does not become an integer), so the string "1", the number 1 and `true`
  are distinct. The width is not promised (Android returns the boxed type that was set, with `sbyte`/`ushort`
  stored as `int`, `uint`/`ulong` as `long` and `decimal` as `double`; iOS returns `long` and `double`), so
  compare with `Convert` rather than a cast. A container set natively (not through this API) reads as a
  `Dictionary` on Android and as its JSON text on iOS. Reports still show the natural value.
- iOS launch and relaunch now send `wrapper_info` (type, version, build, metal, fps) unless the caller supplied
  one. This changes the SDK's video capture to its Unity path. `fps` is `Application.targetFrameRate` (30 when
  unset), never above `Screen.currentResolution.refreshRate` because the SDK uses it as a frame-skip divisor; it
  is read once at launch. A caller-supplied `wrapper_info` is kept only when it is a map whose `type` is a
  non-empty string; anything else is replaced, with a warning. Not yet validated on a device.
- Android lifecycle events reach C# through the wrapper only, so events fired before C# starts (auto-launch,
  crash recovery) are replayed once, in order, when the listener is attached.
- `Debug.LogException` called from a background thread now reports (it used to throw `UnityException` from the
  dedupe clock and report nothing).

### Fixed

- iOS: `SetAttribute`/`GetAttribute` crashed on string, number and bool values (`NSJSONSerialization` rejects a
  bare scalar).
- iOS: the wrapper channel survives `Stop` and `DeleteCollectedDataOnDevice`; the SDK never redelivers it, so
  clearing it silenced channel logs, network events and breadcrumbs for every later launch.
- iOS: `DeleteCollectedDataOnDevice` could leave the managed hooks installed over a stopped SDK while it was
  still launching; `Relaunch` never marked the SDK as launched.
- iOS: launch options with a tab or other control character, nested maps or lists, enums, or NaN/Infinity now
  produce valid JSON (they used to produce JSON the SDK rejected, so launch options silently fell back to
  defaults).
- iOS: the managed-upload cancel state is lock-guarded; the no-SDK stub compiles.
- iOS: the injected "Bugsee Upload Symbols" Run Script failed every iOS build with "Permission denied" (the script is
  written without an executable bit); it now runs through `sh` and cannot fail the build.
- iOS: dSYMs are generated for every build configuration of Unity-iPhone and UnityFramework
  (`DEBUG_INFORMATION_FORMAT=dwarf-with-dsym`, `GCC_GENERATE_DEBUGGING_SYMBOLS=YES`; opt out with
  `BUGSEE_NO_DSYM_FORCE` or the Bugsee > iOS menu toggle).
- iOS: the "Bugsee Upload Symbols" Run Script uploads for every Xcode configuration, Debug included (it used to
  skip all but Release unless `BUGSEE_UPLOAD_ON_DEBUG=1`); `BUGSEE_SKIP_UPLOAD_ON_DEBUG=1` skips Debug. An export
  appended over one made by an earlier version has its old failing phase replaced.
- Android: the pre-launch wrapper provider is injected into the generated manifest. Unity 2021.3 does not merge
  a package's loose `Plugins/Android/AndroidManifest.xml`, so it was missing from the APK and early registration
  never happened (a crash recovered on the next start was assembled without the wrapper).
- Android: the JNI completion callbacks work: `BooleanCallback1Proxy` never matched the unboxed `Boolean` the SDK
  passes (so the delete completion never fired), and the lifecycle listener threw "Ambiguous overloads" at launch.
- Android: `Relaunch` does nothing (with a warning) unless the SDK is `Launched`, as the native call would never
  call back, and a refused `Launch` no longer cancels a pending delete.
- Android: a launch the SDK refuses (made before a stop finished, empty or invalid token) switches the managed
  capture hooks off, without affecting a later launch that works.
- Android: the early wrapper reports the real version and build instead of `"unknown"`.
- Android: the runtime assembly did not compile (`=> checked { ... }` is not valid C#); two scripts lacked `.meta`
  files.
- Exception capture: every main-thread `Debug.LogException` was reported twice (once as an exception, once from
  Unity's log text, with different signatures); the log text is now recognised as the echo of the exception
  (per thread, around the inner `LogException` call), and an exception whose send failed is still reported by
  the echo.
- Android symbols: the R8 mapping Unity writes as `<player>_mapping.txt` was never uploaded; the wrong build's
  symbols zip or mapping could be chosen (another configuration's files looked newer); the IL2CPP linemap was
  skipped for want of a module id, which is now read from this build's symbols zip.
- `Tools~/scripts/update-native-sdks.sh` no longer stops on an offline `git ls-remote` before writing the Android
  identity file (`UnityWrapperIdentity.java`), so Java and C# keep agreeing on the version.

### Notes

- Symbol upload is opt-in via `BUGSEE_APP_TOKEN` and never fails the Unity build.
- The iOS `Bugsee Upload Symbols` Run Script uploads for every Xcode configuration; `BUGSEE_SKIP_UPLOAD_ON_DEBUG=1` skips Debug (replaces `BUGSEE_UPLOAD_ON_DEBUG`).
- iOS linemap UUID upload is performed at Xcode archive time when Unity export has no `UnityFramework` UUID yet.
- Managed `frames[].address`: IL2CPP thrown exceptions get module-relative native IPs when the live stack segment can be paired with them (bottom-anchored, newest first; see the Fixed entry on address pairing); short IL offsets (`[0x00023]`) are ignored.

- iOS filter/report JSON map normalize fail-closed (does not wipe headers/attributes on parse miss).
- Binary report attachments use base64 when bytes are not UTF-8 text.
